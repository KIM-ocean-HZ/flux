你是一位同时理解符号音乐生成、流行音乐编曲、浏览器音频、交互设计与模型评估的研究工程师。请为我的 FLUX 项目做一次从现有事实出发、面向最新可用技术的独立调研。你可以读取 `/Users/hzjin/flux` 的所有项目文件并联网。

## 我的产品目标与疑问

我在做一个网页 MIDI 编曲工作台，帮助创作者发展已经写出的音乐。我希望：

1. 电脑键盘输入 MIDI，模仿 Logic Pro Musical Typing 的主要键位，不需要外接 MIDI 键盘；能试听、录音、编辑。
2. 简易 DAW 有速度、拍号、运输控制、多个轨道、钢琴卷帘。常用音源便于快速试弹，全部生成器可寻址 MIDI 乐器也能选择。不要把“完整目录”悄悄缩成几个预设。
3. 生成结果放到新轨，可与源轨用相同音色。支持叠加播放、Mute、Solo、保留、丢弃、重新生成，不覆盖原轨。
4. 现有生成听起来杂乱、不可用于作品。目标风格更接近现代流行乐，不希望只在民歌或玩具旋律上展示。
5. 我不想被 AMT、LoRA 或六种规则变换的旧计划绑住。可以保留、替换、组合或暂不采用，只要证据充分。
6. 我想知道 **TypeSafe 的 Jev** 能否快速做 MIDI 候选选择／概率判断；这里说的是 Jev，不是 JEPA。
7. 我想知道能否通过 MCP、CLI 或结构化工具调用，让 LLM 直接参与编曲；也接受专用音乐模型、规则伴奏或组合方案。

请独立验证而不是照抄下面这些待核事实：

- 网页建议后端仍是随机 stub；网页并未调用 AMT，不能把网页随机音符的听感当成 AMT 质量。
- 研究管线使用已经预训练的 AMT；FLUX 没有训练过模型，Essen 只是候选输入池。不要把“民歌训练坏了模型”当成事实。

- `melody_to_controls()` 只处理 program 0；研究管线随后主动混入 controls；检查采样器是否已分离生成与输入，以及同 program 聚轨的边界。
- 检查 `ops.max_time()` 是否包含音符时值，生成终点是否错把最后 onset 当作选区末尾。
- 检查 AMT 是否丢失 velocity、CC、拍号、弯音、同音色轨道身份；分别说明什么是词表限制、什么是当前转换器限制。
- 原 pilot 是否混用 top_p、缺少种子／重复、对混合 MIDI 算指标，以及计时是否包含加载和网络。
- 当前机器硬件与当前进程实际可见设备要分开记录；有 MPS 参数或 Mac wheel，不代表已达到可用速度。

先输出“已实现／只是文档计划／确定性缺陷／待测质量假设”的短表。不要为了重整而重写项目。

## 三、网页 DAW 与最直觉的交互

请查 Apple 官方 Musical Typing 文档／图示，核实真实键位。给出一套可执行规格，覆盖：

- 音符键、黑白键映射、八度、力度、延音、复音；哪些照搬 Logic，哪些因浏览器快捷键／可访问性调整。
- 试听、实时录音、步进输入分别何时写入音符；录音准备轨与选中轨是否一致；按键松开、失焦、换轨、切八度和取消时如何释放声音。
- 拍、tick、秒、BPM、拍号的单位；4/4、3/4、6/8 的区别；速度修改是否改变音符位置；量化、倒数、循环、节拍器的最小行为。
- 轨道／片段／音符／乐器／音源资源的最小数据模型。`trackId`、GM program、MIDI channel 不是同一件事。两条相同音色轨要能独立 Mute/Solo/音量。
- 完整 GM 128 melodic programs 与鼓的编号关系；常用预设＋完整分类搜索；音源按需加载与资源体积。
- 对比原生 Web Audio、Tone.js、SpessaSynth、smplr 等实际可用方案；区分时钟、合成器、SoundFont、MIDI 文件解析库。
- 分别核查引擎代码许可与音色资源许可；提出可以实际使用的资源候选及其体积、加载方式、再分发条件，未知必须标明。
- 电脑键盘不依赖 Web MIDI；外接 MIDI 的浏览器权限与 Safari／Chrome 兼容单独考虑。
- Mute/Solo/录音准备、源轨参考选择、生成轨默认音色、候选比较、保留／丢弃／重生成、撤销及迟到响应的行为。
- 适合初次用户的布局图、最短主流程、错误／空输出状态，以及可操作的验收样例。

请区分首轮可听工作台、后续生成集成、以后再做的高级能力。不要为了像 DAW 就扩成插件宿主、完整混音台、账号和云协作产品。

## 四、重新调查音乐模型与表示

广泛发现，再优先评估真正适合 FLUX 的候选。至少覆盖：

- 事件自回归模型、按小节／按轨 infill、扩散或掩码式符号生成。
- 专用音乐 LLM、ABC／乐谱规划、结构化 MIDI 生成。
- 钢琴模型与通用多轨模型的差异。
- 音频生成、音频到 MIDI、分轨／转录作为可选旁路的价值和损失，不能用好听音频演示替代可编辑 MIDI 验收。
- 节拍／小节、和弦、轨道角色、音域、密度、风格标签与表现力控制。
- 音乐 tokenization（如 REMI/MMM 等）、MidiTok、Symusic 等基础设施；更换 tokenizer 是否与已有权重兼容。

可以从 AMT、MIDI-GPT、Aria、MIDI-RWKV、music2music／REMI-z、GETMusic、MIDI-LLM、Text2midi、SkyTNT Midi-Model、MuPT、MusicLang 等名字开始，但必须独立查当前状态并寻找遗漏，不能只复述名单。对新出现的音频／混合系统，只在确实能帮助 FLUX 时纳入。

每个进入最终比较的候选至少记录：

1. 正确项目身份、发布日期／版本、论文、官方代码、模型卡、实际权重入口。
2. 输入输出、条件化方式、续写／伴奏／补全任务、现有旋律保留能力。
3. 独立同音色轨道、目标小节、可控角色与乐器覆盖。
4. tempo／meter／力度／踏板的表示与损失。
5. 模型参数、权重大小、CPU／MPS／MLX／CUDA 的文档支持与实测区别。
6. 训练语料及流行风格覆盖，有无与测试集重叠风险。
7. 代码许可、权重许可、数据许可分别是什么；缺失信息与访问门槛。
8. 公开证据具体证明了什么；是否只是演示；是否有可复现比较。
9. 适配 FLUX 的最小实验、工程成本、失败条件。

不要宣称某模型“全面超过 AMT”，除非有同任务、同输入、同评价的证据。给出按任务的优先级：流行旋律加贝斯／鼓／和弦、同音色变奏、钢琴续写可能需要不同选择。不要因模型更新就默认更好。

## 五、Jev、LLM、MCP、CLI 与候选判断

先确认 TypeSafe Jev 的当前官方入口、可用版本、输入模态、Choice／Score／Noul、概率与 confidence 的语义、价格、上下文、延迟测量条件、数据处理政策与访问资格。

请特别研究：

- 它能否理解 MIDI 数字列表，还是需要由代码抽取音程、节奏、和声与轨道角色再判断？如何验证而不是猜测？
- 概率分布、模型信心、校准和音乐质量有什么区别？候选都差时如何拒绝？对中文需求是否可靠？
- 意图分类、工具选择、风格标签、4–8 个候选排序是否合适；逐音符选择为什么可能合适或不合适？请给可反驳的论证。
- 官方已公开的计数、数值、逻辑或提示敏感性限制；独立论文／复现实验是否已发现相关问题。
- 与精确代码规则、普通 LLM、音乐嵌入／检索、监督学习排序器的必要性与成本比较。
- 使用相同候选池，怎样测 Jev 的增益，避免把生成器改善算到排序器头上。

再研究 LLM 参与编曲的路线：直接输出音符 JSON；和弦／结构计划再由代码展开；调用专用生成器；读取工程后批量编辑；多候选生成与批评重排。

核查真实存在的 Logic、Ableton、REAPER MCP／CLI／脚本接口和音乐 agent 项目。区分官方 API 与社区桥接、源码可用与本机可运行、结构化读写与 UI 自动化。考虑状态回读、撤销、重复请求、权限和维护成本。不要仅因为有 MCP 就说模型懂音乐。

给出最小工具契约，并说明是否应先做 CLI 再包 MCP、怎样让 HTTP／CLI／MCP 共享同一业务层。工具操作应产生可验证的候选，不直接把任意模型文本当 shell／Python 执行。音频调度不应等待远程模型逐音符响应。

## 六、更贴近流行乐的数据

不要仅以“文件数量大”排名。区分 MIDI、MusicXML、ABC、音频、音频转录 MIDI、单钢琴、真正多轨及描述标签。

调查 POP909、Pop1K7、Lakh、MetaMIDI、GigaMIDI、Slakh、MAESTRO、Aria-MIDI、MidiCaps、PDMX 及新的可用数据。每项至少写：风格、规模的口径、角色／和弦／节拍标注、来源、质量问题、访问门槛、实际许可、适合训练还是评价。

分别讨论使用数据、微调、发布衍生权重、分发 MIDI 和商业产品的条件；不要把 GitHub MIT 代码许可当作所有歌曲版权授权。条件未知就说未知，不推断无权或有权。

给出可执行的数据准备：流行风格定义、人工抽查、和声和轨道角色识别、坏文件过滤、重复／移调版／同作品多编配处理、先按作品划分再切片、基座模型训练污染检查。我自己的原创或明确可使用的音乐应如何进入评估集？

明确回答：哪些问题可能通过更好的条件和采样解决，哪些需要风格适配，哪些可能需要换模型？什么时候 LoRA／state tuning 值得做，什么时候停止？不要直接建议从零大规模训练。

## 七、将“杂乱”变成可诊断问题

建立假设表，至少涵盖：网页 stub 与真实模型混淆、音源／音量、MIDI 导出和单位、末音窗口、和弦上下文、同时生成太多乐器、采样、稀疏输出、重复旋律、节拍与句法、训练域、缺少力度表情。

每个假设写最小证伪实验、控制变量、预期观察和对应动作。可以先做 6 段四小节、少量种子的开发诊断，再扩大到多输入多种子正式比较；数量可调整但要说明目的和资源。

测量至少分开：

- 工程正确性：原轨保持、轨道／范围遵守、非法音符、空输出、失败率、取消／过期响应。
- 音乐特征：密度、复音、音域、节奏稳定、和弦关系、重复与变化。
- 实际可用性：统一音源下的开发者试听、偏好与编辑成本。没有进行就明确写没有，不编造分数。
- 效率：冷加载、热生成、完整请求、音频可听时间、p50/p95、设备内存与成本。

固定版本、权重 hash、tokenizer、seed、输入 hash、条件、全部输出与失败，避免选择最好的一次。正式参与者研究与开发者自评分开说明，沿用学校的实际要求，不推定已有审批。
