## 用户目标

在网页中像简易 DAW 一样录入 MIDI：电脑键盘沿用 Logic Musical Typing 的主要键位；项目可设置速度和拍号；少量常用音源便于快速试弹，完整生成器可寻址乐器集合可搜索选择。用户生成时创建独立建议轨，可继承相同音源，支持叠加、Mute/Solo、保留、丢弃和再生成。结果必须能试听、编辑和导出。

**和弦是明确的控制输入。** 弹入／导入／编辑 MIDI 后自动显示识别出的和弦，允许多种解释；也能手选根音＋大小三和弦、add、sus、七和弦及低音。系统根据前后文和可纠正的调性分析级数与和声进行。用户确认的和弦保持固定，R0、音乐模型和 LLM 规划读取同一份和弦轨；自动分析不能悄悄改掉用户选择。

“生成的音乐根本不可用、杂乱无章”是用户的当前试听反馈，应优先解决。它是有效的问题输入，但尚不是有盲测设计的统计结果。不能用“管线已通”代替音乐可用性，也不应先假定只有训练规模这一种原因。

## pipeline 与 core 是什么关系

`research/pipeline.py` 是实验编排：准备输入、转为 AMT controls、调用模型、保存音乐、计算指标。它回答“怎样跑一次生成并保留结果”，没有定义用户要做哪一种音乐发展。

`core/transforms.py` 提供用户可明确指定的精确编辑：模进、倒影、逆行、增值、减值、片段重复。这些操作也适合作为无模型对照。它们不是伴奏生成的必要步骤，更不能自动把杂乱输出修复成流行乐。

保留这段已经测试的代码，将其放入选区的可选“变换”菜单；主流程是“弹入 → 确认／选择和弦 → 按角色生成另一轨 → 比较 → 保留”。纯鼓等不依赖和声的任务可直接生成。没有必要让所有生成先做一次倒影或强迫用户学习六种算法。旧方案的“变换 → 模型修复 → 约束”仅保留为可单独验证的研究假设。

## 原旋律与同音色建议轨

用户提出的独立同音色新轨适合试听比较，复制的是乐器与音源设置，不是原音符。需要同时维护三个不同身份：

- `trackId`：项目内轨道，例如“钢琴旋律”和“钢琴建议”。
- `program/isDrum`：MIDI 乐器类别；两轨允许相同。
- `origin/generationId`：原输入、变换或某次模型生成的来源。

当前安装的 `anticipation.sample.generate()` 返回前通过 `ops.split(tokens)` 分开 controls；在 FLUX 当前 `inputs=None` 调用中，可直接保留生成事件。`pipeline.py` 随后主动 `ops.combine(..., controls)` 才得到研究用混合物。适配器应在合并之前返回新增内容，源轨保存在项目状态中。

AMT 的 MIDI 导出器按 instrument 聚轨，无法代替 DAW 的任意轨道身份。生成与源旋律同音色时，不能先把混合 MIDI 导出再按 program 拆分，更不能按音高／时间差集删除重复，合法齐奏也可能被误删。项目导出需要独立轨道与通道安排。

保留候选就是将建议轨变成正式轨；源轨始终保持。Mute/Solo 只影响监听，默认不改变生成参考集合。模型自己重复了原旋律属于另一个质量问题，独立新轨不能保证它不会模仿。

## 已确认的现状与待验证原因

| 项目 | 证据级别 | 结论 |
|---|---|---|
| 网页旧根地址 404 | 已复现并修复 | 后端原先没有 `/`；与模型加载无关 |
| 网页 Suggest 随机 | 代码确认 | 网页建议听感不可用不能算 AMT 失败 |
| Essen 训练模型 | 原假设错误 | Essen 仅是输入池，FLUX 没有训练过模型；AMT 使用外部 Lakh 预训练权重 |
| 末音生成范围 | 本地源码确认 | `ops.max_time()` 取最大 onset，不包含 duration；当前样例 8 秒，传入生成终点为 7 秒 |
| 首个 control | 本机复算确认 | `sample.generate()` 的 clip 实际丢弃前 50ms；当前样例 14 个 control 只保留 13 个 |
| 源演奏表情 | 本地依赖源码确认 | 当前 AMT 编码／重建没有保留完整 velocity、CC、弯音等；原轨不能经过该路径往返保存 |
| 混轨后的来源配对 | 本机产物复核 | 同音高重叠使时值／来源配对不唯一；按 onset＋pitch 扣除原旋律只能作历史诊断，不能作新候选来源证明 |
| 稀疏与停止条件 | 源码机制确认，因果待测 | 采样到越界 onset 即停止；先记录原因并对照实验，不直接认定是 medium 稀疏的原因 |
| 设备回退记录 | 源码确认 | CPU 回退后日志仍可能记录最初设备；新运行器记录实际设备，旧行不能证明是否发生回退 |
| 目标轨保证 | 代码与旧产物确认 | 允许集合 mask 不保证目标轨非空或合适，两组约束 pilot 贝斯为零 |
| 模型／约束优劣 | 证据不足 | 单输入、无重复且 top_p 不同；旧计时不含整个交互流程 |
| 民歌风格导致全部混乱 | 待验证假设 | 需相同模型下比较流行、民歌等输入，并控制其他变量 |
| 更多训练就会更好 | 待验证假设 | 先排查表示、窗口、条件、采样、音源，再验证小规模风格适配 |

时间窗口和生成边界的问题本轮只定位，未改研究管线、未覆盖历史 MIDI 或 CSV。模型比较前在新适配器和运行器中做确定性回归并修正，保留旧 pipeline 作为历史基线；新实验写入独立 run 目录。组合修复的听感提升不能直接证明各缺陷的因果贡献。

## 已纳入计划的技术方向

| 层 | 当前建议 | 理由及尚需验证的部分 |
|---|---|---|
| 编辑与播放 | 保留 React；统一整数 tick 项目时间、独立轨道与片段；验证完整 GM 合成器 | 先使音乐可听、可弹、可比较，避免由模型事件编码定义全部产品 |
| 精确音乐操作 | 保留 core 与普通代码验证 | 节拍、音域、音符合法性等不需要远程模型计算 |
| 生成 | **R0 和弦轨＋角色 pattern 先跑通完整闭环**；AMT 与 MIDI-GPT 做模型比较；Aria 续写另测 | R0 是强制基线，质量仍待验收；CA2、AccoMontage2 补入可选候选池，先核验适配与权重条款 |
| 和声与结构 | **和弦轨为一等对象**；自动识别显示、手动选择、上下文级数／进行、确认后控制生成 | 区分即时识别与旋律配和声；根音、类型、加音、低音、时间和来源都须保存；允许歧义与用户纠正 |
| 文本意图与工具 | LLM 输出计划、参数和批量编辑；共享函数先包 CLI，再按需包 MCP | 可让外部助手操作同一项目；协议本身不提供音乐能力 |
| 快速选择 | Jev 作为意图路由／候选排序实验 | 仅文本输入，概率不是音乐质量；时间与音高运算仍由代码负责 |
| 数据 | 原创流行片段＋POP909；多轨用 Slakh 或筛选后的 GigaMIDI/Lakh | 按任务与来源选，先小规模诊断，之后才判断训练收益 |

## 执行顺序与验收

1. **A：可听工作台与和弦输入。**先验证音频，再实现键盘／录音、多轨、BPM／拍号、完整 GM、项目保存；接着实现 MIDI 和弦自动显示、手选 add／sus 等、上下文级数／进行，验收 CH-01–CH-08。
2. **B：和弦控制与 R0。**冻结原轨和确认的和弦快照，角色优先生成贝斯／鼓／铺底，支持同音色候选、比较、撤销、取消／stale；完成 CH-09–CH-12。从纯旋律建议配和声可随后加入，不阻塞手动和弦路径。
3. **E0：公平生成契约与诊断。**可随 A/B 准备；修正窗口、首 control、来源、时间单位和实际设备日志，保留历史文件。假采样器验证通过后才做模型比较。
4. **C／E1–E2：先小比较，再扩展。**六段流行材料先分离诊断因素，用 R0 对照；再比较 AMT、MIDI-GPT。首轮不直接展开 486 次矩阵；先实测单次耗时、列组合预算。钢琴续写独立比较；全部输出及重试记录，按作品汇总偏好，不把多 seed 当独立作品。
5. **LLM／Jev 可选试验。**LLM 按既定和弦规划角色与 pattern，和弦修改作为候选；先固定候选池，再比较随机、规则、Jev 与普通 LLM 排序，中英文分层。CLI／HTTP／MCP 共用契约，具体模块拆分随实现决定。
6. **有证据再适配。**若主要问题确实是流行乐风格或伴奏写法，再做筛选子集的 LoRA／state tuning；训练、验证、测试按作品隔离。停止无收益训练同样是合理结论。

以上是依赖顺序，不是新的硬日期或已获导师批准的研究方案。LLM 工具路线可以与生成器小比较并行验证；不要先造复杂代理系统再寻找音乐任务。
